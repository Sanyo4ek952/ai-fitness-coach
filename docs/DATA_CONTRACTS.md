# Контракт обмена данными v1 — проект спецификации

## IMP-04 — явный пустой RIR плана

Для duration/distance поле rir в предписании/override/setPlans может отсутствовать либо быть null; null сохраняется при импорте, хранении и экспорте. Числовой RIR и rirMax для них недопустимы. Это согласует runtime с уже опубликованной JSON Schema и не удаляет данные. Для reps правила диапазона прежние; схема фактических подходов не менялась. Результаты проверок и read-only валидация файла владельца — PROGRESS.

## IMP-02 — расширение программ (26.11.2026)

Актуальный контракт и ограничения описаны в [PROGRAM_EXCHANGE](PROGRAM_EXCHANGE.md); полная [JSON Schema](../examples/training-program.schema.json) и [8-недельный пример](../examples/training-program.periodized.example.json) генерируются/проверяются по Zod. Optional definition/setPlans/rirMax, duration.maxSeconds, phases/progressionRules/recommendations, курсор и снимок этапа сохраняются через import/accept/review/backup/rollback. schemaVersion остаётся 1, DB v4/native40 и stores прежние, старые записи не переписываются. Прежние ограничения каталога и reviewAfterSessions ниже — исторические, заменены IMP-02. Старые и новые responseSchema сохранённых запросов читаются без изменения пакета.

## M7-01 — provenance принятого предложения в backup (26.11.2026)

При `acceptance.response.decision=propose_program` восстановленная версия обязана иметь `previousId === request.context.programVersionId`: initial создаёт первую версию с previousId=null, review создаёт непосредственного преемника своей активной версии. Совпадения draft/profile/time недостаточно: нельзя перепривязать подтверждение к другой позиции цепочки, даже если планы и timestamps совпадают. Preview и restore повторно отклоняют такой граф до записи; исходные данные/поколение остаются прежними. Общий regression-case пройден fake-IDB и native Chromium. Форматыbackupv1/DBv4/DTOv1 и совместимость корректных копий не изменены.

## M6-03 — явное полное удаление

Public API `training.privacy.preview(): {expectedToken,counts:[{name,count}]}` только читает все10stores. `privacy.erase(expectedToken,confirmed)` требует literal true; сравнивает полный снимок внутри общей rw transaction, затем clear всех stores и put случайного неперсонального restoreGeneration. Все исторические ревизии, AI-запросы/ответы/подтверждения/analysis snapshots, активное занятие/таймер, замеры и Blob удаляются вместе. Повреждённый доменный payload не препятствует очистке обычных JSON-envelopes. Token учитывает ID/metadata immutable фото, без чтения байтов. Изменение после preview/другое удаление/restore → отказ без частичного удаления. Ошибка финального tombstone → rollback всех stores и возможность явного повтора.

Технический маркер не попадает в backup/AI и не содержит личных данных. DBv4/native40 и DTO неизменны. Старые страницы не могут записать или восстановить сохранённый preview даже при совпадении доменных ревизий; reopen не снимает page-generation guard. После полного reload можно создать новый профиль или явно восстановить внешний backup. Старые скачанные копии/чаты/оригиналы пользователь удаляет отдельно; приложение не обещает отозвать уже переданные данные. Отдельное удаление замера/отзыв питания не переписывает историю — для полной очистки используется этот явный сценарий.

## M5-03 — питание (25.11.2026)

Новых полей/миграций нет: nutritionOptIn в профиле/снимке запроса и nutritionTips0–3×180 в ответе уже валидируются Zod. Без согласия снимка непустой ответ отклоняется. `coach.nutrition()` читает транзакционный текущий профиль, baseline анализа, acceptance и исходный request; повторно проверяет ответ по запросу. Только принятый baseline активной версии и совпадающая ревизия профиля дают советы. Новый экспорт/preview/reject не изменяет выбор, пустой keep не наследует старый список; rollback без acceptance даёт пустой список. Отказ скрывает вывод, не удаляет исторические пакеты/ревизии. Старые DTO и literal instructions сохранены.

Реализация: Zod-схемы как источник истины; JSON Schema включена в каждый запрос. С M2-01 оба examples проверяются целиком. M2-02 добавила initial-экспорт/импорт/предпросмотр, M2-03 — явное атомарное принятие и начальную последовательность. Текущая граница DB v4 описана в дополнении M5-02; исторические ограничения ниже относятся к состоянию соответствующих задач.

## M3-03 — актуальное дополнение: отдых, замены, пропуски (25.11.2026)

DB остаётся v3/native30: таблицы и индексы прежние. WorkoutSession допускает optional `restTimer` (null либо {id, startedAt, deadline}), optional `replacements` (до 20 записей {plannedExerciseId, originalExerciseId, actualExerciseId, timestamp}) и отдельный конечный status=`skipped`. Старые сессии без новых полей читаются без переписывания; новые поля не заполняются плановыми фактами. Прежний код со strict-схемой не умеет читать расширенные записи: откат приложения требует совместимой версии, данные не очищать. Изменения схемы сессии не меняют сохранённые запросы/ответы ИИ, версии программы и снимки.

`sessions.timer({sessionId, expectedTimer, timer})` заново читает текущую active-сессию в транзакции четырёх таблиц, сверяет её позицию/программу и точный baseline таймера (отсутствие нормализуется в null). Продолжительность положительная, не более 600 секунд; startedAt не раньше начала занятия. Устаревшая остановка не стирает новый deadline другой вкладки. Точный повтор — чтение. Таймер не является тренировочным фактом и не повышает historyRevision. Остаток = max(0, ceil((deadline−now)/1000)); tick не пишет в БД, при focus/visibility/reload берётся текущее время. Истёкший deadline остаётся доступен до явного удаления/нового запуска. Finish атомарно очищает таймер. Фоновые уведомления/звук не реализованы.

`sessions.action` принимает strict discriminated-команду `replace` или `skipSets`, sessionId и expectedHistoryRevision. Замена — отдельное явное действие только в active, одна на строку, пока есть незаписанные подходы. Фильтр каталога: одинаковое измерение и первая (основная) мышечная группа, помощь тренажёра не смешивается с отягощением. Фильтр не оценивает противопоказания, доступность инвентаря или безопасность методики; UI предлагает выбирать знакомый подходящий вариант либо пропустить. Количество/цель/отдых исходного плана не меняются, вес на новую форму не переносится. Исходные done сохраняют actualExerciseId; новые done обязаны соответствовать выбранной замене и иметь timestamp не раньше её события. Исправление done не меняет происхождение. Повторная замена строки в MVP недоступна.

`skipSets` содержит 1–20 подходов исходной схемы со status=skipped: без actual и rir, с исходным и выбранным упражнениями. Один подход или все оставшиеся упражнения записываются атомарно; занятые слоты не перезаписываются. HistoryRevision повышается на 1 за команду, курсор не меняется. Done+skipped завершается partial; только skipped без done при обычном finish — abandoned без сдвига. Пропуски не превращаются в выполненные результаты. Точные повторы обеих команд не пишут и не повышают ревизию, иные устаревшие действия отклоняются. Любой отказ откатывает все записи команды.

`sessions.skipWorkout` принимает те же поля, что startSessionSchema, но создаёт отдельное событие-сессию status=skipped, startedAt=endedAt=момент явного действия, sets=[], без тренировочных фактов. Допускается только при отсутствии active: активную тренировку сначала продолжить/завершить, результаты не удаляются. В одной транзакции sessions/programState/counters проверяются cursor/history, добавляется событие, позиция сдвигается на (index+1)%N и historyRevision повышается ровно на 1. Повтор того же ID/источника возвращает прежний skipped даже после нового старта; чужой ID/другая позиция/устаревшая история отклоняются. Start не использует ID skipped для открытия active; низкоуровневый save не создаёт skipped в обход курсора. В AI recentSessions по-прежнему разрешены только completed/partial, skipped не является выполненным занятием.

UI сохраняет открытые черновики и baseline при чужом done/skipped/замене. Для новой замены нужно явно закрыть прежний ввод и открыть новую форму; для уже пропущенного слота отправка отключена, черновик можно прочитать и закрыть. Подтверждения привязаны к historyRevision. После действия контролы блокируются ещё на 500 мс, чтобы второй клик не попал в действие следующего экрана.

## AI request
UTF-8 JSON, schemaVersion=1, kind=coach_request, UUID requestId, createdAt ISO UTC, mode=initial/review, context: profileRevision, programVersionId (null при initial), historyRevision (монотонный номер фактических данных). profile: goal (строка 1–500), experience (beginner/intermediate/advanced/unknown), sessionsPerWeek (1–7 или null), equipment (IDs, unknown допускается), optional details (отсутствуют либо null), nutritionOptIn (boolean). Поле program — активная версия либо null; recentSessions — до 20 последних завершённых/частичных, агрегаты historySummary (детерминированные; сгруппированные по упражнению/единицам), reasonCodes. exerciseCatalog — допустимые упражнения с ID, русским названием, оборудованием, типом измерения. instructions — полная инструкция, responseSchema — полная машиночитаемая схема. Включать до 90 дней измерений по релевантным цели типам, только по согласию на AI-экспорт; не включать имя, контакты, сырые фото, EXIF или другие не нужные данные. Перед скачиванием пользователь видит категории данных; фото прикладываются вручную отдельно, если выбраны.

## AI response
Общие поля: schemaVersion=1, kind=coach_response, requestId, context (точная копия версий запроса), decision (`propose_program`, `keep`, `needs_input`, `unsupported`), summary (до 300 символов), reasons (до 5 строк по 240 символов), nutritionTips (0–3 строки по 180 символов; пустой массив если нет согласия). Discriminated union: `propose_program` требует proposedProgram; `keep` допускается только если есть активная программа; `needs_input` требует question (до 240 символов, ровно один существенный вопрос); `unsupported` требует краткую безопасную альтернативу в summary. Другие поля варианта запрещены.

## Program DTO

IMP-01: самостоятельный файл готового плана — строгий `{ "schemaVersion": 1, "kind": "training_program", "program": <Program DTO> }` без requestId/context/внутренних UUID. Источник схемы `model/program-import.ts`, пример `examples/training-program.example.json`. Скачиваемая инструкция содержит JSON Schema и канонический каталог, без пользовательских данных; просит только оформить исходный план, не менять упражнения/нагрузку. UTF-8/JSON и лимит2MiB проверяются тем же чтением, что и AI-ответы. В выделенной форме своего плана можно явно извлечь proposedProgram из строго валидного propose_program-ответа; остальные поля пакета отбрасываются, запрос в БД не подделывается. Keep/needs_input/unsupported не являются готовой программой. Обычный `readCoachFile`/coach.importResponse не меняет поведения.

`programs.previewImport` валидирует файл и оборудование в read-only транзакции, возвращает полный файл, прежнюю программу и локальный CAS-token (профиль id/revision, последняя версия, курсор, historyRevision, baseline). Никаких pending-записей или автоприменения. `applyImport` требует true-согласие, повторно проверяет token/оборудование/отсутствие active/хронологию, атомарно добавляет новую версию и первый курсор. Старые AI-пакеты/история не переписываются. Двойное применение прежнего token блокируется. Принятия AI-анализа/советов не создаётся; baseline новой версии определяется существующим fallback по дате/профилю версии, как при возврате к прежнему плану. Формат DBv4/backupv1 прежний.
`title` (1–100), `goalInterpretation` (1–240), `workouts` (1–14 шаблонов, порядок массива — порядок занятий), `reviewAfterSessions` (1–14, подсказка для анализа, не автоматическое изменение). Каждый шаблон: `title` (1–100), `exercises` (1–20), каждый элемент: `exerciseId` из каталога, `sets` (1–20), `target` discriminated union: `reps` (min/max 1–100, min<=max, `weightKg` finite 0–1000 или null), `duration` (seconds 1–7200, optional intensity text), `distance` (meters 1–100000, optional intensity text), `restSec` (0–600), `rir` (0–10 или null, только для reps), `note` (до 240, необязательно). Границы — техническая валидация, не разрешённая нагрузка. Нестандартный объём/интенсивность вызывает отдельную доменную проверку; опасные рекомендации блокировать, неизвестные — показать как требующие оценки. Упражнения с весом собственного тела могут иметь weightKg=0, null означает неизвестный внешний вес; для ассистированных упражнений тип нагрузки каталога и факт должны отличать помощь от отягощения. Без каталога и сопоставимого типа не сравнивать нагрузку. Для timed/distance MVP хранит факт по соответствующей единице, не вычисляет тоннаж.

После импорта присвоить внутренние UUID программе/шаблонам/строкам; внешние названия не являются ключами. Сформировать diff в приложении (а не доверять текстовому описанию от ИИ), включая удалённые/добавленные упражнения, последовательность, параметры и новую интерпретацию цели. Применять полный снимок атомарно после явного подтверждения всех изменений. Если решение keep — подтвердить принятие анализа, не создавать программу.

## Фактическая тренировка
WorkoutSession хранит шаблон и снимок плана. ExerciseSet: идентификаторы исходного и фактического упражнения, index, status done/skipped, фактический target соответствующего типа, nullable rir, timestamp, optional note, optional pain flag. Факт не подменяется планом; вес/повторения предзаполнены, но становятся фактом только при сохранении. История тренировок включает partial/abandoned и отдельные события skipped, однако агрегаты исключают незаполненные подходы. Операции редактирования повышают historyRevision.

## Импорт (порядок)
1. Размер JSON ≤ 2 MiB (рабочий лимит); читать как UTF-8, parse, неизвестные версии отклонять. Проверять схему strict, массивы, длины, конечные числа, опасные ключи, недопустимые типы, без исполнения данных.
2. Проверять requestId, совпадение контекста с сохранённым запросом и текущими ревизиями, допустимость mode/decision, принадлежность ID каталогу, equipment/constraints, nutritionOptIn. Не применять ответ от другого запроса, при изменении фактов предложить новый экспорт.
3. Проверять доменные ограничения; несоответствия показывать по-русски. Никакой частичной записи. Предпросмотр diff. Запретить применение при активной тренировке; подтверждение повторно проверяет ревизии в транзакции.
4. Записать proposal, новую неизменяемую версию и курсор атомарно; статус request=accepted. Повторное применение requestId невозможно. Отклонение не меняет действующий план; тот же запрос можно переимпортировать до принятия, если актуален.

Backup: отдельный kind=fitness_backup, отдельная version; экспорт профиля, истории, всех версий, настроек и при явном выборе фото в архиве. Ограничить распакованный размер, количество записей и изображений, не извлекать пути из архива на устройство. Валидация всех связей до замены. Проверить round-trip и rollback. AI-ответ не является резервной копией.

## Реализованный доменный срез M1-01 (24.11.2026)

Источник истины для реализованных типов — `src/entities/training`, public API `index.ts`. В M1-01 добавлены профиль, каталог, черновик плана, внутренняя версия программы, шаблон, подход и сессия со снимком. На момент M1-01 полные AI-конверты и хранилище отсутствовали; последующие срезы M1-02/M2-01 описаны ниже. Backup, замеры/фото и события пропуска целого занятия пока не реализованы.

Уточнения неоднозначных мест спецификации без изменения продукта:

- Порядок занятий/строк — порядок массивов, отдельное поле order не дублируется. `programVersion.id` — UUID неизменяемой версии, `previousId` связывает её с предыдущей; отдельный ID семейства программ пока не нужен. Первая revision=1 требует previousId=null, последующие требуют другого UUID. Наличие предыдущей версии и монотонность относительно сохранённой истории проверит репозиторий.
- `rir` необязателен у reps, допускает null; отсутствие и null означают неизвестную оценку, ноль означает известный нулевой запас. Для duration/distance поле запрещено, в том числе null. `weightKg` у reps обязателен как число или null. В факте допустим неизвестный вес: он не заменяется плановым или нулём.
- Фактический target reps содержит `reps`, не min/max. Время/дистанция хранят конечные положительные значения в секундах/метрах; дробные значения допустимы, повторы/количество подходов — целые. Вес от 0 до 1000 кг — техническая граница, не рекомендация. Собственный вес не прибавляется к `weightKg`: там только добавленная нагрузка. У assisted-pull-up это величина помощи, больший вес не означает большую нагрузку.
- Каталог фиксирует `load.type/unit/basis`: для пары гантелей — вес одной гантели (`per-dumbbell`), для goblet — общий вес, для тренажёра — указанная нагрузка его стека. Разные упражнения/тренажёры и помощь/отягощение не становятся сопоставимыми из-за одинаковой единицы kg. Каталог из восьми записей намеренно мал: три упражнения из синтетического примера, жим ногами из прототипа, собственный вес/помощь и по одному примеру времени/дистанции. Инструкции тренировочной техники и чужие лицензируемые подсказки не включены; названия/метаданные составлены для проекта.
- `ExerciseSet.plannedExerciseId` — UUID строки снимка; `originalExerciseId` и `actualExerciseId` — стабильные ID каталога. Данные плана не копируются повторно в каждый подход: они доступны по строке `plannedSnapshot`. Замена сохраняется в факте, не меняет снимок; сейчас допускает то же измерение, что исходное упражнение, но не объявляется безопасной или сопоставимой.
- status=skipped не содержит actual/rir; пропуск не результат. У active endedAt=null, у завершённых состояний — UTC timestamp не раньше старта. completed требует все выполненные подходы, partial — непустую часть, abandoned сохраняет имеющиеся факты. Проверяются локальные связи, уникальность ID и пары строка/index, время подходов внутри занятия. Сохранение/редактирование и historyRevision появятся в последующих задачах, атомарность пока не заявляется.
- Дополнительные сведения профиля (`details`) и каждое поле допускают отсутствие/null. Начальный набор: возраст взрослого, рост, вес, длительность, доступные веса, ограничения, сон, питание. Числовые диапазоны технические; отсутствие не блокирует старт. Замеры/фото не превращаются в поля анкеты. equipment=[unknown] не смешивается с известными ID; это отсутствие знания, не разрешение на любое оборудование.

Схемы не принимают лишние ключи, не исполняют текст и не выполняют запись/отправку данных. Zod возвращает отдельные объекты, вложенные массивы/объекты readonly и заморожены. Это защита снимка в памяти, а не гарантия неизменяемости БД. Проверка доступного инвентаря, ограничений и безопасности предложений, сверка внешних ревизий и атомарное применение остаются обязательными в M2/M3; структурно валидный план не означает физиологически безопасный.

## Форма профиля M1-03 (24.11.2026)

`features/edit-profile` использует существующий `profileSchema` и репозиторий без изменения DB/доменного контракта. При монтировании экран открывает БД, читает current и закрывает соединение при уходе. Состояние экрана — базовая прочитанная ревизия для optimistic concurrency и временный черновик формы, не альтернативное хранилище. При StorageConflictError читается последняя ревизия. Сравниваются базовая ревизия, черновик и последнее сохранённое значение. Независимые изменения объединяются только по нажатию пользователя, конфликтующие поля требуют выбора одной из двух сторон. `details` разрешается как один блок с отображением всех значений. Новый UUID не создаётся поверх существующего профиля; новая попытка получает его UUID и revision+1, а репозиторий атомарно проверяет актуальность повторно. При очередном изменении БД требуется новое разрешение конфликта, автоматического overwrite/retry нет. Старые ревизии, программы, снимки, сессии и historyRevision не меняются. Реальный профиль не передаётся в синтетическое демо или внешний сервис.

Общий historyRevisionSchema используется и адаптером. Чистые createWorkoutSession/finishWorkoutSession проверяют исходную версию/шаблон/снимок, временные границы и выбирают следующий курсор; input не меняется.

`sessions.overview()` читает активную программу/курсор, единственную активную сессию с проверкой связи со снимком и historyRevision одной r-транзакцией. Повреждение/несколько active — ошибка, не пустая история. `sessions.start` в одной rw-транзакции четырёх таблиц проверяет курсор и ревизию, создаёт active с пустыми sets и снимком текущего шаблона, повышает historyRevision на 1, не двигает курсор. Повтор того же ID/источника возвращает сохранённую сессию, включая уже завершённую (никогда не открывает её заново). Два разных ID из вкладок при текущей active возвращают ту же сессию без второй записи/ревизии. При отсутствии active новая попытка требует точный expectedHistoryRevision: это защищает от старого старта даже после полного цикла A/B→A либо abandoned с той же позицией. Resume в UI — только чтение/раскрытие, без записи и смены startedAt.

`sessions.finish` заново читает факты, проверяет единственную active, её связь с текущей позицией и expectedHistoryRevision. completed — выполнены все подходы; partial — выполнена непустая часть; без done — abandoned. Completed/partial переводят позицию на (index+1)%workouts.length; abandoned без результата оставляет позицию. Это не явный пропуск целого занятия: он остаётся M3-03. Статус/endedAt, курсор и +1 historyRevision пишутся в одной транзакции. Ошибка любой записи откатывает всё. Повтор завершённого sessionId возвращает прежний результат без нового сдвига/ревизии, даже если уже началось другое занятие. Подтверждение со старой ревизией после новых фактов отклоняется. Низкоуровневый sessions.save запрещает обход finish при переводе существующей active-сессии действующей программы в конечное состояние; исторические исправления фактов прежнего конечного статуса по-прежнему возможны.

План и факт не смешиваются, старые версии/snapshots не меняются. Пропуск даты/возврат/смена профиля не двигают курсор. AI-accept уже проверяет active в своей транзакции; одновременные start/accept сериализуются по общим таблицам. UI записей подходов, таймер/замены/пропуски не добавлены. Проверки completed/partial используют синтетические записи репозитория, не объявляются готовым пользовательским logging-сценарием.

## M3-02 — атомарная запись факта (25.11.2026)

`sessions.recordSet({set, expectedSet, expectedHistoryRevision})` принимает strict-команду через recordSetSchema. set переиспользует exerciseSetSchema, допускается только done. expectedSet=null означает новый подход, иначе это точный показанный исходный факт. Новый факт разрешён только в active и без замены упражнения. Успешная запись сессии и +1 historyRevision атомарны; курсор/план/версии не пишутся. Ошибка откатывает оба put. Команда завершения M3-01 остаётся единственной операцией продвижения курсора. DB остаётся v3, миграций нет.

Фактические повторы обязательны по существующей схеме (целое 1–100); новые обязательные сведения не введены. Единицы и границы переиспользованы. Ошибка записи сохраняет ввод для повтора, факт показывается из IndexedDB/liveQuery.

Реализован `coach.createReviewRequest(requestId, createdAt, expectedToken)`: одна rw-транзакция прежних exchangeTables читает актуальный профиль, activeProgram, baseline принятого анализа, control, historyRevision, все версии/сессии; сверяет token M4-01 и целостность каждого снимка с исторической версией. ## M5-02 — добровольные замеры и локальные фото (25.11.2026)

Актуальная БД v4/native40 добавляет только `bodyMeasurements: id` и `progressPhotos: id`; v1–v3/stores/indexes не редактируются, старые записи не переписываются. Откат приложения требует совместимой версии, очистка БД недопустима. Тестовые будущие миграции обновлены до v4→v5.

`bodyMeasurementSchema`: strict `{id:UUID, kind:weight|waist|hips|chest|thigh|arm, value:finite positive, unit:kg|cm, measuredAt:ISO UTC}`. Weight только kg, ≤500; окружности только cm, ≤300. Это технические ограничения, не нормы здоровья. До1000 записей. Будущая дата отклоняется на записи. По одному ID нет перезаписи; исправление — явное удаление и новое добавление. Список от новых к старым, равные даты по ID; вывод без округления малых дробей в0. История упражнений/профиль автоматически не изменяются.

`measurementRevision` — отдельный монотонный counters key, отсутствие допустимо только при пустой таблице; чтение не создаёт его. Добавление/удаление существующего замера и повышение ревизии атомарны; точное повторное удаление отсутствующего ID ничего не пишет. Ошибка обработки/лимита/quota не создаёт запись; подготовленная копия при отказе записи остаётся в UI для явного повтора или отмены. Это временный черновик, при закрытии страницы он теряется. Удаление в UI требует явного подтверждения; внешние копии/оригиналы не удаляются.

AI request schemaVersion1 допускает **optional** strict `measurements: BodyMeasurement[]` ≤1000; без отдельного выбора поле отсутствует. Старые сохранённые запросы/примеры прежнего формата читаются, instructions/response schema/ответный context не меняются. На экране Тренера шесть unchecked показателей: пользователь сам выбирает релевантность своей свободной цели и соглашается на включение только этих типов в конкретный экспорт/копирование. `selectMeasurements` валидирует весь вход/duplicate ID, выбирает диапазон [createdAt−90×24ч,createdAt] включительно, сортирует measuredAt DESC/ID ASC, не мутирует вход. В DTO не допускаются фото/Blob/EXIF/filename/внутренние счётчики. Согласие не сохраняется настройкой и не включается автоматически при новом посещении экрана.

Согласованный экспорт читает замеры/ревизию и прежний контекст в одной транзакции. Для opted запроса envelope хранит внутренний `measurementRevision` (не в DTO); import/preview/accept сверяют его с текущим в прежней общей транзакции, поэтому add/delete после экспорта или preview требуют нового запроса. Для обычного запроса без замеров их изменение не делает контекст устаревшим. Прежние baseline/profile/history/active/snapshot проверки сохранены. Удаление замера не стирает сохранённый AI-request с его историческим снимком; об этом предупреждает UI. Удаление таких пакетов и backup/restore — M6.

Фото никогда не входят в обычный AI-JSON. Для внешнего ИИ пользователь отдельно выбирает один локальный снимок, видит предупреждение о чувствительном содержимом/внешнем сервисе и подтверждает скачивание очищенной JPEG-копии. Приложение не передаёт файл в сеть; пользователь сам прикладывает копию в выбранный чат. Замеры/фото не вызывают физиологических оценок, процента жира или автоматической смены программы. M5-03/backup/PWA не реализованы этой задачей.

## M6-02 — backup v1 / DB v4 (25.11.2026)

Источник схемы: `entities/training/model/backup.ts`. `kind=fitness_backup`, `version=1`, `databaseVersion=4`, `createdAt` UTC, `photosIncluded` и `data` с именами всех10stores. Сохраняются storage-envelopes/ключи, неизменяемые profileRevisions/programVersions, sessions/status/plannedSnapshot/sets/replacements/restTimer, historyRevision/measurementRevision, requests/response/acceptances с local baselineKey/measurementRevision, activeProgram/cursor и analysisBaseline/Control/Snapshot, замеры. При отдельном выборе все текущие progressPhotos сериализуются как metadata+канонический base64 JPEG (Blob восстанавливается с прежними байтами). photosIncluded=false требует пустого progressPhotos. Старые AI-снимки замеров могут пережить удаление текущих замеров; это сохранённые данные копии, не скрытый новый экспорт ИИ.

JSON-архив без сжатия/ZIP/путей: ≤96MiB до чтения/после arrayBuffer, fatalUTF-8; ≤20000records суммарно, ≤10000в каждой основной таблице,≤1000замеров,≤20фото×2MiB/1600px; глубина≤64,≤2млнузлов, опасные ключи запрещены до рекурсивной Zod-валидации. JPEG: длина/base64/MIME/размеры/заголовок, запрет EXIF/XMP/IPTC/comment segments, native Image.decode при наличии. Node header-only проверка не заменяет native decoder. Неизвестные версии не мигрируются молча; это первая версия backup. DBv1→v4 по прежним миграциям может экспортироваться в backupv1 без выдуманных курсора/счётчиков.

Проверяется весь граф: совпадение ключей/envelopes, уникальность/непрерывность ревизий и цепочка previousId/время/профили, sessions→точные версии/снимки, active≤1 и соответствующий cursor, request→profile/program/recentSessionIDs/снимки/history/measurementRevision и baseline его версии, response→request/context/domain, acceptance→request/response/версия/время/полный proposedProgram, baseline/control/snapshot→существующие записи/факты. Сохранённые старые review exports без baseline допускаются как прежде, provenance не выдумывается. Их последующее применение по-прежнему требует нового экспорта.

Восстановление только полной заменой всех10stores после предпросмотра и явного true-подтверждения, без merge. Текущее active занятие блокирует restore; active из копии разрешено. CAS предпросмотра учитывает все текущие JSON-records и immutable фото по ID+metadata; через публичный адаптер фото не заменяются под тем жеID. Ревизий недостаточно (таймер/control/фото не обязательно их повышают). Validation/decoder завершаются до rw. В одной транзакции повторный CAS,clear/bulkAdd всехтаблиц и новый локальный counters.restoreGeneration(UUID). Ошибка в любой точке откатывает всё. restoreGeneration не экспортируется: это поколение локальной страницы, не доменная ревизия. Все write-операции адаптеров сверяют его в той же транзакции; старые страницы/их новые краткоживущие connections требуют полного reload. Старое приложение доM6-02 такого guard не имеет — перед восстановлением закрыть другие вкладки и обновить приложение. DB schema/native40 и прежние версии миграций не менялись.
